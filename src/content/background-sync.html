If you only read this

  1. You can't keep an app alive in the background. Make every step safe to kill and resume.
  2. The UI reads only the local database. A write goes to the DB and an outbox in one transaction.
  3. A sync engine pushes the outbox with idempotent op_ids and pulls changes by a server sequence cursor.
  4. Files travel separately: hashed, split into parts, uploaded straight to object storage, checkpointed per part.
  5. The OS runs the work: WorkManager on Android; BGTaskScheduler and background URLSession on iOS. React Native keeps this native.

01The basement upload

A field engineer finishes an inspection in a basement with one bar of signal. She taps Submit on 40 photos, watches a spinner, and swipes the app away to take a call.

In most apps those photos are now in limbo. In a well-built one, nothing is lost. The upload pauses. The OS wakes the app when signal returns. Only the parts that never reached the server are sent again, and she never has to think about it.

This post is about building the second app, and about explaining how you built it to a hiring panel.

02The rule the OS enforces

Both platforms protect battery and memory by stopping apps that are not on screen. Here is what your code can do in each state.

ForegroundRunsRunsDo anything
Just backgroundedRuns briefly, then cachedA few seconds via beginBackgroundTaskFinish the current write

KilledMemory pressure, Force Stop, OEM battery killersMemory pressure, user swipeNothing. Only disk survives

If it isn't on disk, it doesn't exist.

Every design decision below follows from that line. Pending edits live in a table. Upload progress lives in a table. The sync position lives in a table. The process is disposable.

03Explain it like a restaurant

When an interviewer says "explain it to me simply", use a busy restaurant. Every part of the system has a counterpart that everyone already understands.

The waiter writes the order on a pad before walking to the kitchen.→Local write + outbox row, one transaction
Every ticket has a unique number. The kitchen ignores a ticket it already cooked.→op_id idempotency on the server
The kitchen screen numbers every dish it sends out, in order.→Server sequence number per partition
A waiter back from break asks "what happened since dish 1041?"→Pull changes by cursor
The "86" board lists dishes taken off the menu.→Tombstones for deletes
The manager says "we're full, come back in ten minutes, not all at once".→429 + Retry-After + jitter
A catering order goes out tray by tray, each tray signed for.→Multipart upload, checkpoint per part
A waiter's shift ends mid-order. The next waiter picks up the same pad.→Process killed, job resumes from disk
Say it out loud"Think of a restaurant. The waiter writes every order on a numbered ticket before going to the kitchen, so nothing is lost if he's interrupted. The kitchen ignores duplicate tickets and numbers every dish it sends out. Anyone coming back from a break just asks what happened since the last number they saw. My sync engine works the same way: local outbox, idempotent op IDs, and a server sequence cursor."

04The architecture on one screen

06Sync in four moves

1

Write locally

Row + outbox entry in one transaction. UI updates now.

2

Push

Send outbox ops with op_id. Server dedupes and orders them.

3

Pull

Ask for changes since the cursor, one page at a time.

4

Commit

Apply the page and save the new cursor in the same transaction.

Push first, so the server sees your edits before it answers what changed. Here is the whole contract.

// push: idempotent by op_id
POST /v1/sync/push
{ "ops": [{ "op_id": "018f3c7a-9b", "entity": "note", "id": "n-77",
            "type": "update", "base_version": 12, "fields": { "title": "Pump room B" } }] }
→ { "results": [{ "op_id": "018f3c7a-9b", "status": "applied", "version": 13, "seq": 1042 }] }

// pull: ordered by server sequence, never by timestamps
GET /v1/sync/pull?cursor=c_1041&limit=500
→ { "changes": [ { "seq": 1042, "entity": "note", "id": "n-77", "version": 13, "fields": { … } },
                 { "seq": 1043, "entity": "note", "id": "n-12", "deleted": true } ],
    "next_cursor": "c_1043", "has_more": false }
Why not updated_at?Device and server clocks drift, and two rows written in the same millisecond can both be skipped. A server sequence gives one total order and a safe place to resume.

08Moving huge files

Records and bytes are different problems, so they get different pipelines. A file upload is a small state machine, and every state is a value in a table.

Captured→Hashed→Already on server?→Uploading parts⇄Paused→Completing→Done
  • Copy first. Copy the file into app storage. A gallery URI can disappear.
  • Hash it. SHA-256 lets the server say "I already have this" and verify the result.
  • Split it. S3 multipart parts of 8–16 MB (minimum 5 MB, except the last).
  • Go direct. Presigned part URLs send bytes straight to storage, never through your API.
  • Checkpoint. Save each part's ETag the moment it lands. A kill costs one part at most.

class UploadWorker(ctx: Context, p: WorkerParameters) : CoroutineWorker(ctx, p) {
  override suspend fun doWork(): Result {
    val t = repo.get(inputData.getString("fileId")!!) ?: return Result.success()
    for (part in t.missingParts()) {          // resume from the DB
      if (isStopped) return Result.retry()
      repo.markPartDone(t.id, part.n, repo.put(part))  // checkpoint each part
    }
    repo.complete(t.id); return Result.success()
  }
}

  • Doze and App Standby Buckets slow down rarely used apps. OEMs like Xiaomi and Oppo kill harder, so test on them.
  • Force Stop cancels all scheduled work until the user opens the app again.

// iosMain (Kotlin Multiplatform): iOS schedules it, the shared Kotlin engine does the work
fun registerSync(engine: SyncEngine, scope: CoroutineScope) {
  BGTaskScheduler.sharedScheduler.registerForTaskWithIdentifier("com.app.sync", usingQueue = null) { task ->
    scheduleNextSync()                                  // always re-schedule first
    val work = scope.launch { engine.runOnce(budget = 25.seconds) }
    task?.expirationHandler = { work.cancel() }         // the OS wants its time back
    work.invokeOnCompletion { task?.setTaskCompletedWithSuccess(!work.isCancelled) }
  }
}
  • A swipe-kill cancels background URLSession transfers. Resume from your saved parts on next launch.
  • With .complete file protection the DB is unreadable while locked. Use completeUntilFirstUserAuthentication for sync stores.
  • Silent pushes are throttled. Treat them as hints, never as a schedule.

12Interview kit

I design for the app being killed. The UI reads only a local SQLite database, every write lands in an outbox in the same transaction, and a sync engine pushes it with idempotent op IDs and pulls changes by a server sequence cursor. Files go separately as checkpointed multipart uploads straight to S3. The OS runs it all: WorkManager on Android, BGTaskScheduler and background URLSession on iOS.

Mobile OSes stop background apps to save battery, so I never try to stay alive. I persist intent instead. A user edit writes the row and an outbox entry in one SQLite transaction, so the UI is instant and works offline. When the OS runs our job, the sync engine pushes outbox ops with client-generated op IDs, which the server dedupes, so retries are always safe. Then it pulls changes after its cursor, a server-assigned sequence, and saves the new cursor in the same transaction as the data. Conflicts are chosen per entity: last-write-wins for low-value fields, a 409 and merge for important records, operations for counters. Large files are hashed, split into parts and uploaded through presigned URLs, with each part checkpointed, so a kill costs one part at most. On Android that's WorkManager and user-initiated data transfer jobs; on iOS, BGTaskScheduler and background URLSession; in React Native the same native modules, with JS only observing the DB. The backend is stateless with a partitioned change log, CDN snapshots for first install and coalesced push hints, so it scales horizontally.

Worked examples to reach for

When a panel says "give me a concrete example", pick the one closest to their product.

Field inspection app

200k technicians · 2 GB photos each per week

That's about 400 TB of uploads a week, so bytes must go direct to S3 with dedupe by hash and lifecycle rules to cheaper storage. Sync only each technician's assigned jobs. Prefetch job packs on Wi-Fi and charging. Compress photos on device before upload.

The follow-up they'll ask"What if a tech is offline for three weeks?" Deletes are tombstones with a 90-day TTL. Past that, the server returns 410 and the app rebuilds from a CDN snapshot, then pulls deltas.

Clinic booking app

appointment slots · patient notes · offline front desk

Bookings are server-authoritative: the app proposes a slot offline and shows "pending confirmation". Notes use 409-and-merge so no clinician's edit is lost. Patient data is encrypted at rest with keys in Keystore or Keychain.

The follow-up they'll ask"Two receptionists book the same slot offline." The server accepts the first and returns 409 for the second. The app shows the conflict and offers the next free slot.

Retail point of sale

stores keep selling during an outage

Sales write to a local ledger. Inventory changes are operations ("−2 units"), not new totals, so two tills never overwrite each other. Every sale carries an op_id, so replaying after reconnect can't double-charge or double-count.

The follow-up they'll ask"Can you take cards offline?" Only as store-and-forward with a per-transaction limit, which is a business risk decision. Say who signs off on that risk.

Rapid-fire answers

How do you keep the app running in the background?
You don't. Both OSes will stop it. Persist intent on disk and let WorkManager or BGTaskScheduler run short, resumable jobs.
What survives a kill?
Only disk: SQLite rows, the outbox, the cursor and saved upload parts. Anything in memory is gone.
Push or poll?
Both. A coalesced push hint triggers a pull. A periodic job and app-foreground sync are the fallback, because push is best effort.
How do deletes reach a device that was offline?
Tombstones in the change log with a TTL. If the device's cursor is older than the TTL, the server returns 410 and the device rebuilds from a snapshot.
How do you stop a retry storm after an outage?
Full-jitter exponential backoff on clients, 429 with Retry-After on the server, rate limits per device, and push fan-out spread over minutes.
How do you know sync is healthy?
p95 freshness (time since last successful sync), outbox depth, upload completion rate, conflict rate and background-task expirations, split by app version and device model.
What would you build first with three months?
Outbox, cursor pull, last-write-wins, presigned multipart uploads, OS scheduling and basic telemetry. CRDTs, snapshots and real-time channels wait until the metrics ask for them.

13Glossary and further reading

Outbox
A local table of pending changes, written in the same transaction as the data.
op_id
A client-generated ID per change. The server uses it to ignore duplicates.
Cursor
The last server sequence number the device has applied. It asks for changes after it.
Tombstone
A record saying "this was deleted", kept long enough for offline devices to learn it.
Presigned URL
A short-lived URL that lets the device upload one object straight to storage.
Multipart upload
A large file sent as numbered parts, then assembled by the storage service.
UIDT job
Android's user-initiated data transfer job, for long transfers the user started.
Background URLSession
iOS transfers run by a system daemon, outside your app's process.
